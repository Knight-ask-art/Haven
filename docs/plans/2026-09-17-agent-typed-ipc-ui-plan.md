# Agent Typed IPC 与设置页审批闭环计划

## 目标

在已有 `SettingProposal / SettingChangeReceipt / AgentApprovalToken` Rust 安全内核之上，完成 A1「智能配置推荐」的第一条可验证垂直切片：

```text
设置页内栖伴
  → 读取设置 Agent Context
  → Provider（本阶段尚未接入；无模型时明确显示“无可用模型”）
  → 严格阅读设置 Patch
  → Rust 创建 Agent Proposal
  → UI 展示 canonical digest + Diff
  → 用户点击批准
  → Rust 内部生成并消费一次性 Approval Token
  → 同一 CAS Application Service 写入设置与 Receipt
  → UI 展示 Receipt / Conflict / 零写入结论
```

本阶段要把 Proposal、Approval、Receipt 变成正式的 Typed Application/IPC 能力；不把任意 Agent、模型、SQL、文件系统或 Provider 接入伪装成已经完成。

## 已批准的不变量

1. UI、未来内置 Agent 和外部 MCP 都只能读取受限快照或创建 Proposal；没有任何模型/Provider 能直接写 Settings。
2. Proposal 的 canonical JSON、digest、target、base revision、provenance 由 Rust Application/Domain 生成和校验；前端不得自行计算领域 digest，也不得提交任意 JSON Patch。
3. 本阶段只开放全局 `reading` Section 的严格 Typed Patch；不开放 metadata、rename、filesystem、secret、SQL、Provider 原始响应或任意命令分发。
4. 设置上下文不是作品上下文。新增一个向后兼容的 Agent Settings Subject 表达全局设置范围；旧的内容 Subject JSON 仍必须能够按原 canonical 形状恢复。
5. `agent_settings_context_get` 返回脱敏的阅读设置快照、revision、设置上下文 id/hash 和服务端能力 Manifest；不返回 API Key、Credential、绝对路径、正文或完整媒体内容。
6. 创建 Proposal 必须携带 context id/hash 和 base revision。Rust 重新读取 authoritative 设置并重建上下文，快照过期或 hash 不匹配时 fail-closed，不能用客户端自报的 hash 作为事实。
7. UI 批准命令是唯一的用户确认写入口：调用方提交 Proposal ID 与 UI 显示的完整 canonical digest；Rust 在受控 Application Service 内生成一次性 token、校验绑定、执行 CAS、消费 token、写 Receipt 和迁移状态。
8. Approval Token 原文不出 Rust 内部批准路径，不进入 wire、日志、provenance、Receipt、localStorage 或 React state；现有内部 token 测试入口继续只供 Rust 安全内核使用。
9. 拒绝、digest 不匹配、上下文过期、revision conflict、重复批准和任何应用前校验失败都不得写 Settings；冲突必须有稳定错误码和 UI 可见结论。
10. `HavenClient`、Tauri Client、Mock Client、生成 Wire、命令 manifest、capability JSON 和测试必须同步更新；禁止 `agent_invoke(commandName, arbitraryArguments)`。
11. 没有配置 Provider 模型时，模型选择和 AI 状态显示“无可用模型”；不得显示或推断 `gpt-4o`、示例模型名或模型能力。Mock 只能用于开发/契约测试，并须标识为 Mock/预览，不得冒充真实 AI。

## 本阶段接口

### Read

- `agent_capability_manifest_get`
- `agent_settings_context_get`

第一版上下文只覆盖全局阅读设置；资源偏好、系统硬件、媒体能力、书库统计、设置来源、onboarding 和 periodical context 在后续按独立契约加入，不在本阶段通过“万能上下文”混入。

### Proposal

- `agent_settings_proposal_create`
- `agent_settings_proposal_get`（供 UI 刷新/重开后回读）
- `agent_settings_proposal_reject`

请求字段为闭合 typed DTO：session/request/context id、context hash、base revision、`PreferenceReadingPatchDto`；不接收 SQL、任意 JSON、路径、secret 或自由 command 名。

### Approval / Receipt

- `agent_settings_proposal_approve`
- `agent_setting_change_receipt_get`

批准只接收 Proposal ID + canonical digest。Approval Token 在 Rust 内部一次性生成和消费；wire 只返回 Proposal 状态、变更摘要、applied revision、changed、appliedAt 和脱敏 provenance 投影。

## 验证门

Claude Code 负责实现和补测试，但完成不以其状态消息为准。Codex 必须独立检查：

- 实际 diff 只落在允许范围；`git diff --check` 通过；
- Rust fmt、domain/application/infrastructure 相关测试和 Tauri 编译/测试；
- Wire 生成一致性、Tauri command manifest/capability/ACL 一致性；
- 前端 TypeScript 检查、AI Assistant Vitest 和 IPC Client 测试；
- token 原文没有进入 DTO、错误、日志、React state、localStorage 或生成物；
- stale context、digest mismatch、replay、拒绝、冲突和 Provider 未配置均有测试；
- 明确区分“Mock/本地预览”“代码路径通过”和“真实 Provider/Windows WebView2 未验证”。

## 出口

本阶段完成的定义是：在没有 Provider 的情况下，产品诚实显示“无可用模型”；在受控 Mock/测试入口可以证明 Typed Proposal → UI digest → 用户批准 → Rust 内部 token + CAS → Receipt 的链路；真实 OpenAI/Claude/兼容 Provider、MCP、Skill、资源偏好和硬件推荐仍保持未接入状态。
